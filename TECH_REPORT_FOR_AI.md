# Технический отчёт по форку `scdlbot` (для глубокого анализа другим ИИ-ассистентом)

## 1. Общий обзор проекта

Проект представляет собой Telegram-бот для поиска и скачивания музыки по ссылкам и текстовым запросам с приоритетом качества аудио. В форке реализован «унифицированный» сценарий: пользователь может отправить ссылку или просто `исполнитель + трек`, после чего бот ищет лучший источник, скачивает, при необходимости конвертирует и отправляет файл в Telegram.

### Что умеет бот

- Обрабатывать прямые ссылки на музыкальные платформы и видеохостинги.
- Обрабатывать текстовые запросы (поиск трека без ссылки).
- Выполнять quality fallback:
  - сначала релевантные платформы и YouTube;
  - затем кроссплатформенный поиск;
  - затем быстрый web fallback (DuckDuckGo), если включён.
- Оценивать кандидатов по качеству и релевантности (lossless/bitrate/sample rate/высота видео/title match).
- В форке добавлен интерактивный выбор варианта (inline-кнопки), если найдено несколько релевантных источников.
- Отправлять пользователю аудио с детализированной подписью (теги, формат, размер, качество) и обложкой.
- Поддерживать русскоязычный UX (команды, кнопки, сообщения).

### Основные технологии

- Язык: Python 3.11+ (в репозитории также указан `runtime.txt` для cloud runtime).
- Telegram API: `python-telegram-bot` (асинхронная архитектура).
- Скачивание/извлечение:
  - `yt-dlp`
  - `scdl`
  - `bandcamp-dl`
- Обработка медиа:
  - `ffmpeg` (внешняя бинарь, обязательна для полного пайплайна)
  - `mutagen` (чтение/обогащение тегов)
- Конкурентность:
  - `concurrent.futures.ThreadPoolExecutor`
  - `pebble.ThreadPool` (в форке выбран по умолчанию для стабильности).
- Метрики и наблюдаемость:
  - `prometheus_client`
  - `sdnotify` (systemd watchdog).

## 2. Структура репозитория

Ниже укороченное дерево с ключевыми файлами и назначением.

- `scdlbot/`
  - `__main__.py` — главный entrypoint `scdlbot`, регистрация хэндлеров, роутинг апдейтов, скачивание, отправка в Telegram, настройки, fallback-логика.
  - `quality_fallback.py` — модуль оценки качества, поиска кандидатов и выбора лучшего источника.
  - `texts/` — текстовые шаблоны сообщений бота (help/settings/errors и т.п.).
  - `utils.py` — вспомогательные утилиты для работы с URL/файлами.
- `flacbot/`
  - `__main__.py` — входная точка альтернативного режима `flacbot`.
  - `bot.py` — логика ответов/поиска для FLAC-ориентированного режима.
  - `search.py` — поисковая логика в контексте `flacbot`.
  - `texts/` — шаблоны текстов `flacbot`.
- `scripts/`
  - `cloud_preflight.sh` — preflight проверки окружения (poetry, ffmpeg, env).
  - `run_cloud_bot.sh` — запуск бота в cloud-режиме (в т.ч. dry-run).
- `cloud_startup.sh` — bootstrap cloud-среды, установка Poetry/зависимостей.
- `Makefile` — команды установки, preflight, cloud run, тесты.
- `pyproject.toml` — зависимости, entrypoints (`scdlbot`, `flacbot`) и tooling.
- `.env.sample` / `.env.cloud.sample` / `.env.flacbot.sample` — шаблоны переменных окружения.
- `Procfile` — запуск для PaaS-сценариев.
- `render.yaml`, `Dockerfile.render` — deployment-конфигурация для Render/Docker-сборки.
- `telegram_settings/` — файлы с командами/настройками для BotFather.
- `README.rst` — базовая документация исходного проекта.
- `CLOUD_SETUP.md` — cloud runbook для форка.
- `SEARCH_WORKFLOW.md` — детальная схема flow поиска/скачивания (добавлено в форке).
- `AGENTS.md` — инструкции для агентной разработки в cloud.

### Явное выделение ключевых узлов

- Главная точка запуска `scdlbot`: `scdlbot/__main__.py`
- Telegram-хэндлеры (апдейты/команды): в основном `scdlbot/__main__.py` (command/message/callback handlers)
- Скачивание и обработка музыки:
  - `scdlbot/__main__.py` (оркестрация загрузки/отправки)
  - `scdlbot/quality_fallback.py` (поиск/оценка кандидатов)
- Кэширование/персистентность:
  - `PicklePersistence` в `scdlbot/__main__.py`
  - chat-level state в `context.chat_data`
- Логирование:
  - конфигурация logging и основные логи в `scdlbot/__main__.py`
- БД:
  - отдельной реляционной/NoSQL БД в текущем форке нет.

## 4. Логика работы бота

### Сценарий A: пользователь отправляет одну ссылку

1. Апдейт попадает в message handler в `scdlbot/__main__.py`.
2. Из сообщения извлекается URL (или несколько URL; в этом сценарии один).
3. Выполняется первичная попытка прямой обработки:
   - определение источника;
   - вызов соответствующего загрузчика (`yt-dlp`/`scdl`/`bandcamp-dl`).
4. Если прямое скачивание неуспешно:
   - извлекается query hint из метаданных ссылки или текста;
   - запускается fallback-поиск (`find_better_source` / high-quality search).
5. Кандидаты ранжируются по релевантности + качеству.
6. Если кандидат один — сразу скачивание; если несколько — показ inline-выбора.
7. После загрузки:
   - при необходимости конвертация/разбиение;
   - чтение тегов через mutagen;
   - сбор подписи (источник, артист, трек, альбом, год, жанр, качество, формат, размер);
   - поиск/подготовка обложки.
8. Отправка файла(ов) пользователю через `send_audio`/`send_video`.

### Сценарий B: пользователь отправляет несколько ссылок

1. Сообщение парсится на список URL.
2. Каждая ссылка проходит через общий пайплайн обработки.
3. В зависимости от настроек чата (`flood`, режим) бот может отправлять результаты пакетно/последовательно.
4. Состояние и промежуточные результаты фиксируются в `chat_data`.
5. В случае ошибок по отдельной ссылке бот продолжает обработку остальных, отдавая пользователю диагностическое сообщение.

### Сценарий C: команды `/start`, `/help`, `/settings`, `/search`, `/dl`, `/link`, `/restart`

- `/start`:
  - быстрый ответ + вывод справки;
  - вывод reply-клавиатуры с русскими кнопками.
- `/help`:
  - отправка `help.tg.md`.
- `/settings`:
  - отображение и изменение режимов чата (скачивание/ссылки/ask и пр.).
- `/search <query>`:
  - явный запуск поискового сценария;
  - при нескольких вариантах — интерактивный выбор качества.
- `/dl <url>`:
  - форс-режим скачивания и отправки файла.
- `/link <url>`:
  - показать прямые ссылки/результаты без скачивания файла.
- `/restart`:
  - доступ только владельцу (`TG_BOT_OWNER_CHAT_ID`);
  - self-restart через `os.execv`.

### Как устроен pipeline (поиск/скачивание/конвертация/отправка)

- Поиск:
  - выделение query из текста/URL/метаданных;
  - параллельный discovery кандидатов (YouTube, платформы, web fallback);
  - параллельный probe качества по кандидатам.
- Оценка:
  - title match ratio;
  - lossless/bitrate/sample rate;
  - YouTube video height (HD-priority, `YOUTUBE_MIN_HEIGHT`).
- Скачивание:
  - выбор загрузчика по источнику;
  - fallback на `yt-dlp` при необходимости.
- Пост-обработка:
  - ffmpeg-конвертация и/или split для лимитов Telegram;
  - mutagen-теги;
  - генерация thumbnail.
- Отправка:
  - `send_audio`/`send_video` с детализированной подписью;
  - очистка временных файлов.

### Отличия от «классического» исходного `scdlbot` (в текущем форке)

- Существенно расширен quality fallback и ранжирование.
- Добавлен dedicated YouTube HD-приоритет (1080p+) для лучшего аудио-источника.
- Добавлен интерактивный выбор качества при множественных результатах.
- Улучшены извлечение query и точность fallback для Bandcamp/VK.
- Русифицированы команды/кнопки/сообщения для всех пользователей и scopes.
- Улучшены UX и устойчивость `/start`/`restart`/быстрых кнопок.

## 5. Логирование и мониторинг

### Где ведётся логирование

- Основной `logging`-стек в `scdlbot/__main__.py`.
- Логи по обработке апдейтов, ошибкам загрузки, исключениям Telegram API, ошибкам fallback.
- В ряде мест включены `exc_info=True` для traceback.
- Опционально поддерживается Syslog (`USE_SYSLOG`).

### Логируются ли входящие запросы пользователей

- Частично: факт вызова команд и технические события по обработке апдейтов логируются.
- Возможны логи с `user_id/chat_id` и текстом/URL в отдельных ветках обработки.
- С точки зрения privacy/security нужно проверить и минимизировать хранение сырого пользовательского контента в production-логах.

### Логируются ли ошибки скачивания/отправки

- Да: ошибки загрузчиков (`yt-dlp/scdl/bandcamp-dl`), ошибки Telegram send API, таймауты и исключения fallback обычно логируются.

### Куда пишутся логи

- По умолчанию: stdout/stderr (под cloud/process-manager сбор логов).
- При включении syslog: в системный лог.
- Отдельной БД/лог-хранилища в кодовой базе не обнаружено.

### Мониторинг

- Метрики Prometheus (`Counter`, `Gauge`) присутствуют:
  - количество/типы запросов;
  - состояние очереди executor (в форке отражено в логике метрик).
- Есть интеграция с `sdnotify` для watchdog в systemd-сценариях.

### Что стоит усилить в первую очередь

- Единый структурированный формат логов (JSON) для корреляции событий.
- Явная маскировка токенов/секретов при любых exception dumps.
- Корреляционный request-id на весь pipeline запроса.
- Отдельные счётчики ошибок по типам источников (vk/bandcamp/youtube/soundcloud).

## 6. Кэш и временные файлы

### Используемые механизмы кэша/состояния

- `PicklePersistence` (`CHAT_STORAGE`):
  - хранение `chat_data` (настройки чата, временные состояния выбора результата и т.д.).
- Временные директории/файлы:
  - создаются на время загрузки/конвертации/подготовки отправки.
- Временный cache выбора результата:
  - ключи вида `search_choice:<token>` в `chat_data`.
- Возможное повторное использование Telegram `file_id`:
  - зависит от ветки логики отправки, но центральным persistent media-cache этот механизм не является.

### Где хранятся данные

- На диске в рабочей директории/временных каталогах (`DL_DIR`, системный tmp).
- `chat_storage.pickle` (или аналог по env) для persistence состояний.
- Отдельной БД для кэша нет.

### Очистка и риски

- Временные каталоги обычно удаляются после обработки (через `shutil.rmtree`/cleanup ветки).
- Риски:
  - при аварийном падении или kill возможны «хвосты» во временных директориях;
  - рост pickle-файла при долгой эксплуатации без ротации;
  - отсутствие строгой квоты диска может привести к деградации.

### Рекомендации

- Периодический cron-cleanup tmp-директорий.
- Лимит и ротация `CHAT_STORAGE`.
- Алертинг по свободному диску и размеру временных папок.

## 8. Известные проблемы и TODO

### Что найдено по TODO/FIXME/WARNING

- В репозитории встречаются пометки и предупреждения, но ключевые риски в основном операционные (зависимость от внешних источников/API и стабильности загрузчиков), а не «висящие» TODO с критическим долгом.
- В `AGENTS.md` и cloud-документации явно отражены caveats по окружению и запуску.

### Практические ограничения/уязвимые точки

- Источники типа VK/Bandcamp/SoundCloud периодически меняют поведение/антибот-защиту.
- `yt-dlp` и вспомогательные загрузчики требуют регулярного обновления.
- Ошибки сетевого доступа/ограничения region/geo могут ломать pipeline.
- Долгие задачи могут создавать нагрузку на event loop без аккуратного offloading.

### Что может привести к падениям бота

- Невалидный `TG_BOT_TOKEN`.
- Конкурирующие polling-инстансы (Telegram 409 conflict).
- Отсутствие `ffmpeg`.
- Необработанные исключения загрузчиков или Telegram send API.
- Переполнение диска временными файлами.

### Что может привести к блокировкам/санкциям

- Агрессивные массовые запросы к внешним источникам без rate-limit.
- Неправильное обращение с контентом, нарушающим правила площадок.
- Публикация токенов в логах/коммитах.

### Риски утечки секретов

- Коммит `.env`/`.env.cloud` с реальными токенами.
- Логи с полными URL, содержащими приватные параметры.
- Скриншоты/артефакты CI с раскрытыми ключами.

### Рекомендуемые действия

- Принудительная проверка pre-commit на секреты.
- Централизованный redaction токенов в логгере.
- Регулярный security review env-шаблонов и deployment-конфигов.

## 9. Ключевые файлы для детального ревью (10–20)

1. `scdlbot/__main__.py`  
   Главный orchestration-файл: обработка апдейтов, команды, routing, запуск download pipeline, отправка файлов, настройки и управление состоянием.

2. `scdlbot/quality_fallback.py`  
   Ядро quality fallback: discovery кандидатов, probe характеристик, scoring по релевантности/качеству, выбор лучшего источника.

3. `scdlbot/utils.py`  
   Вспомогательные утилиты для URL и вспомогательных операций пайплайна.

4. `scdlbot/texts/help.tg.md`  
   Описывает пользовательский интерфейс команд; важно для проверки соответствия фактическим обработчикам.

5. `scdlbot/texts/settings.tg.md`  
   Текст настроек чата; влияет на UX и ожидаемое поведение режимов.

6. `flacbot/__main__.py`  
   Входная точка альтернативного bot-mode; важно, если в облаке переключают `BOT_MODE`.

7. `flacbot/bot.py`  
   Логика обработки апдейтов в `flacbot`-ветке.

8. `flacbot/search.py`  
   Поисковые функции для FLAC-потока, полезно для сравнения архитектурных подходов с `scdlbot`.

9. `pyproject.toml`  
   Зависимости, скрипты entrypoints, настройки tooling; определяет реальную исполняемую конфигурацию.

10. `Makefile`  
    Сводный интерфейс команд запуска/проверок и cloud-процедур.

11. `cloud_startup.sh`  
    Bootstrap runtime: установка Poetry, зависимости, валидация базового окружения.

12. `scripts/cloud_preflight.sh`  
    Предзапусковые проверки (env + инструменты), критичен для reproducible запуска.

13. `scripts/run_cloud_bot.sh`  
    Операционный запуск бота в cloud-сценарии, включая выбор режима.

14. `.env.cloud.sample`  
    Нормативная схема runtime-переменных для облака; первичный источник правды по env.

15. `.env.sample`  
    Базовый шаблон переменных общего режима.

16. `.env.flacbot.sample`  
    Шаблон переменных для альтернативного режима `flacbot`.

17. `Procfile`  
    Запуск на PaaS-совместимых платформах; важно для анализа production-entrypoint.

18. `render.yaml`  
    Render-деплой декларация: переменные, команды билда/старта, сервисные параметры.

19. `Dockerfile.render`  
    Контейнерная сборка для Render/совместимых платформ.

20. `SEARCH_WORKFLOW.md`  
    Документация с flow/sequence-диаграммами текущей форк-логики (поиск, fallback, конкуренция).

## Итог

Форк существенно расширяет исходный `scdlbot` в трёх направлениях: качество поиска/ранжирования, устойчивость runtime-процесса и русскоязычный UX. Для дальнейшего глубокого анализа другому ИИ-ассистенту целесообразно начать с связки `scdlbot/__main__.py` + `scdlbot/quality_fallback.py`, затем пройти cloud/deploy контур (`pyproject.toml`, `Makefile`, shell-скрипты, `render.yaml`), и только после этого переходить к edge-case анализу конкретных источников (VK/Bandcamp/YouTube/SoundCloud).
